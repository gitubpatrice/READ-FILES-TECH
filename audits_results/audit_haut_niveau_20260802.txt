1. SYNTHÈSE GÉNÉRALE
--------------------------------------------------------------------------------

Verdict : codebase NETTEMENT au-dessus de la moyenne. Aucun Critical. La crypto
du coffre est sérieuse (Argon2id auto-calibré, AES-256-GCM avec AAD, zeroize,
lockout dual wall-clock + monotone), le natif est durci (allowBackup=false,
cleartext off, FileProvider non exporté, anti-zip-slip, R8+shrink), aucun secret
versionné (keystore présent sur disque mais gitignoré et non tracké), zéro
TODO/FIXME, zéro fichier mort, commentaires « pourquoi » exemplaires.

Le code porte les traces de plusieurs itérations d'audit antérieures (F1-F6,
G2-G16, U4) — mais l'audit révèle que les mêmes pièges sont résolus ici et
retombés là : patterns résolus dans un écran, réintroduits dans un autre.

Notes indicatives par axe :
  - Sécurité (MASVS)        : 8,5/10  (L1 atteint, L2 partiel)
  - Qualité de code         : 7/10
  - Architecture            : 6,5/10
  - Cohérence               : 78/100

TOP 5 des problèmes à traiter en priorité :
  1. H1 — Le coffre reste déverrouillé indéfiniment au premier plan
          (pas de lock à la sortie de VaultScreen).
  2. H1(w) — La release GitHub publie un APK universel étiqueté « arm64-v8a »
          (pas de --split-per-abi dans release.yml) ; release sans tests ni
          analyze ni vérification tag↔pubspec.
  3. M3/CI — flutter test || echo "No tests yet" masque les échecs de tests
          en CI ; zéro test sur le vault (feature la plus critique).
  4. H2-H4 — OOM accessibles utilisateur : lectures intégrales non capées
          (recherche de contenu, aperçu explorateur, zip creator).
  5. M1/M2 — Écrasements silencieux de fichiers (copy/move batch, export
          coffre) = perte de données réelle.

2. SÉCURITÉ (agent android-security)
================================================================================

Aucun Critical, aucun High.

MEDIUM
------
S-M1  Permission INTERNET absente du manifest release.
      android/app/src/main/AndroidManifest.xml (INTERNET seulement en
      debug/profile). Double conséquence : (a) UpdateService
      (files_tech_core/lib/src/update/update_service.dart:88) échoue
      silencieusement en release (catch global ligne 141) — le check de MAJ
      est cassé ; (b) À VÉRIFIER : une lib tierce (ML Kit, webview_flutter)
      peut réintroduire INTERNET par manifest merger (aapt dump permissions
      sur l'APK release). À trancher explicitement : ajouter INTERNET ou
      assumer l'app 100 % offline.

S-M2  WebView HTML : sous-ressources distantes non bloquées.
      lib/screens/viewers/html_viewer_screen.dart:104-116 — le
      NavigationDelegate bloque la navigation hors file:// mais pas les
      sous-ressources (<img src=https://…>) chargées même JS désactivé →
      fuite passive d'IP/métadonnées à l'ouverture d'un HTML piégé. Avec JS
      activé (opt-in, avertissement correct), fetch() réseau = exfiltration.
      Atténué par : JS off par défaut + absence d'INTERNET en release (si
      S-M1 confirmé). Correctif envisageable : blocage des schémas http/https
      au niveau ressource ou CSP injectée.

LOW
---
S-L3  Combo MANAGE_EXTERNAL_STORAGE + REQUEST_INSTALL_PACKAGES
      (AndroidManifest.xml:20-21, 39). Justifié métier, documenté (manifest +
      PRIVACY.md §9), acceptable hors Play Store — mais signature « dropper »
      classique si le code Dart était compromis. Risque explicitement accepté.

S-L4  FileProvider expose external-path "." (res/xml/file_paths.xml:19).
      Atténuations solides : exported=false (AndroidManifest.xml:110),
      canonicalisation + racines autorisées + blocklist vault_decrypt/share
      (MainActivity.kt:54-76), grant READ-only. Résiduel : tout le stockage
      partagé est partageable via l'app — comportement voulu.

S-L5  Signature v1 activée (android/app/build.gradle.kts:58) — nécessaire
      pour minSdk 21 mais sensible à Janus (CVE-2017-13156) sur Android 5-7.
      Envisager minSdk 24 pour dropper v1.

S-L6  debugPrint non conditionnés (output_storage_service.dart:120,137) —
      impact quasi nul (no-op en release) mais pattern divergent du reste.

INFO (vérifié sain)

- Keystore et key.properties exclus de git (git check-ignore + ls-files : OK).

- Pas de certificate pinning — acceptable ici (whitelist de hosts, SHA-256

POINTS FORTS SÉCURITÉ

      peut rester posé sur toute l'app.

4. ARCHITECTURE ET STRUCTURE (agent android-architecture) — score 6,5/10
================================================================================

FORCES
------
- Découpage par features clair sous lib/screens/ : explorer/, editors/,
  viewers/ (12), tools/ (22), vault/ ; services/, utils/, widgets/.
- L'explorateur est la feature la mieux structurée (services + widgets fins) —
  modèle à généraliser.
- Package partagé files_tech_core (48 imports) : réutilisation cross-app
  réelle, zéro duplication core↔app.
- Discipline performance : compute()/Isolate avec seuils explicites documentés.
- Hygiène remarquable : aucun TODO, aucun fichier mort, lints durcis et
  justifiés, commentaires qui expliquent les pourquoi.
- State management 100 % setState (239 occurrences / 43 fichiers) : cohérent,
  pas de mélange de paradigmes — mais plafond de testabilité assumé.

FAIBLESSES PRIORISÉES
---------------------
P0 A-P0a  God objects sur la feature la plus sensible :
          lib/services/vault_service.dart = 1352 lignes, ≥4 responsabilités
          (dérivation de clé, I/O chiffré, lockout + SharedPreferences,
          format de backup custom, bridge natif AES) → candidats :
          VaultCrypto, VaultStorage, VaultBackupCodec, VaultLockout.
          lib/screens/vault/vault_screen.dart = 1209 lignes, 8 classes, 21
          setState → éclater par sous-écran.
P1 A-P1a  Absence de DI : singletons (VaultService.instance,
          PanicService.instance), classes statiques (SecureWindow, AppUpdate,
          FileViewerRouter) → impossible à mocker, explique la faiblesse des
          tests. Minimum : injection par constructeur sur les nouveaux écrans.
P1 A-P1b  Duplication réelle de logique métier : docx_viewer_screen.dart:
          82-143 réimplémente l'extraction DOCX alors que extractDocxText()
          existe dans text_extraction_service.dart:82 — risque de divergence
          de parsing.
P1 A-P1c  Tests quasi inexistants : 7 fichiers pour ~21k LOC, zéro widget
          test, vault non testé. Sécuriser le vault par des tests AVANT la
          refonte P0.
P2 A-P2a  Écrans géants : home_screen.dart 1184 l. (6 classes), rft_picker_
          screen.dart 1051 l. (un écran complet placé dans widgets/),
          explorer 974 l. Appliquer partout le découpage de l'explorer.
P2 A-P2b  Dépendances mortes/trompeuses : cupertino_icons (0 import), http
          (utilisé uniquement via files_tech_core qui le déclare déjà),
          flutter_launcher_icons ios: true alors que l'app est Android-only.
P3 A-P3a  Dette de scaffolding : 5 dossiers plateforme inutilisés (ios/,
          linux/, macos/, web/, windows/) ; navigation impérative sans routes
          nommées ; 6 MethodChannels déclarés inline sans registre central ;
          MainActivity.kt (585 l.) concentre tout le natif.
P3 A-P3b  Deux niveaux de « services » sans convention : lib/services/
          (global) vs lib/screens/explorer/services/ (feature-local) — les
          autres features n'ont pas ce découpage.

DIVERS
------
- zip_viewer_screen.dart:168 contient des octets NUL bruts dans un littéral —
  le fichier est détecté comme binaire (casse grep/diff). Réécrire en '\x00'.
- avoid_dynamic_calls / unawaited_futures désactivés globalement
  (analysis_options.yaml:16-18) — assumé et commenté.
- Divergence cross-app : files_tech_core dépend de flutter_markdown (archivé)
